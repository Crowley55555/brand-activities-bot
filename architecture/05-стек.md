## 0. Персональные данные и 152-ФЗ

Да, в продукте есть ПДн граждан РФ: имя, фамилия, телефон, email, telegram_username, UGC-фото с лицами. Это зафиксировано в [01-что-строим.md](01-что-строим.md) и правиле 1 из [00-правила-проекта.md](00-правила-проекта.md). Поэтому **хостинг (место, где всё крутится) и объектное хранилище файлов — только российские, базы данных и файлы — физически в РФ**. Это требование 152-ФЗ («первичный сбор и хранение ПДн граждан РФ — в базах на территории РФ») и это ограничивает выбор провайдеров инфраструктуры и S3-совместимого бакета. На ядро, язык, фреймворк и остальной инструментарий это ограничение не распространяется — там выбор по инженерным критериям.

## 1. Бюджет жетонов (экзотика)

Правило: у стартапа 3 жетона на эксперименты. Ревизия: **потрачено 0,5 жетона из 3**.

- **AI-модель** — не беру в MVP (вся модерация ручная), поэтому 0 жетонов. При появлении в будущем — 1 жетон.
- **Очередь на Postgres SKIP LOCKED** вместо Redis+Celery/dramatiq — 0,5 жетона: приём зрелый (документирован в Postgres с 9.5, 2016 год, Oban для Elixir и ряд питон-библиотек делают ровно это), но менее массовый, чем «Celery+Redis». Решение уже зафиксировано в [04-потоки-данных.md §3.4](04-потоки-данных.md) и даёт реальный выигрыш: одна транзакция на «создал Reward + поставил задачу уведомить», ноль рассинхрона между брокером и БД, ноль лишних демонов для MVP с сотнями задач в день.
- **Jinja2+HTMX для админки** вместо React SPA — 0 жетонов: это самое скучное из возможного (стек существует 15+ лет, HTMX — тонкая обёртка над `fetch`, никакой сборки, никакого TypeScript-build). React для админки на 1 сотрудника на бренд — чистый оверкилл.

Оставшиеся 2,5 жетона держу под будущие потребности (AI-анализ кожи для Бренд A, автомодерация UGC, аналитика второго порядка).

## 2. Выбор по позициям

### 2.1 Язык и версия

**Выбран: Python 3.12** (уже стоит в `pyproject.toml`).

- Альтернатива: Node.js + TypeScript (тоже массово, тоже умеет async/await).
- Почему именно это: автор уже знает Python, экосистема async (FastAPI, SQLAlchemy 2, asyncpg) зрелая, Pillow для Polaroid-рамки — проверенный инструмент, менять язык из-за одной фичи — тратить главное время не на продукт.

### 2.2 Веб-фреймворк и смежный веб-инструментарий

**Выбран: FastAPI 0.115 + uvicorn + Pydantic 2 + pydantic-settings + Jinja2 для админки + HTMX для интерактива** (FastAPI и uvicorn уже стоят).

- Веб-фреймворк, рассмотренные варианты:
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **FastAPI** (выбран) | полноценный async, Pydantic в комплекте, OpenAPI «из коробки», лёгкий, топ-3 по размеру экосистемы в питоне | свой DI не всегда очевиден, admin-UI вручную | ✓ MVP на одного разработчика |
  | Django + DRF | большая батарея, admin из коробки, миграции, auth | тяжёлый sync-рантайм (ASGI есть, но ORM и большая часть кода sync-first), Pydantic неродной, лишнее для чат-бота | нет — админка одна и простая, DRF не нужен |
  | Starlette | минимализм FastAPI без Pydantic-магии | придётся самому дописывать то, что FastAPI уже сделал | нет — FastAPI это и есть «Starlette + Pydantic» |
- Админка — Jinja2 (идёт поставкой с FastAPI через `starlette.templating`) + HTMX для «отклонить/одобрить/отметить пришёл» без полного перезагруза страницы:
  - Альтернатива: React/Vue SPA + отдельный REST — для 3–5 экранов и одного пользователя на мероприятии это тратит недели.
  - Почему именно это: ноль сборки, ноль фронтенд-build, кнопка «одобрить» — это 1 POST + HTMX swap строки таблицы, работает и без JS (как fallback). Это и есть «скучно».

**Запасная альтернатива веб-фреймворка:** Django + Django Admin — если команда вырастет до 3+ бэкендеров и начнётся много CRUD-экранов.

**Почему именно это под мою идею:** FastAPI — минимально достаточный async-фреймворк, прямо соответствует правилу 3 (headless-ядро): HTTP-слой и адаптер Telegram остаются тонкими, бизнес-логика — в `app/core/`.

### 2.3 Адаптер Telegram (отдельный контейнер, stateless)

**Выбран: aiogram 3** (отдельная версия с нативной async-архитектурой, FSM, роутерами). **Запускается в отдельном контейнере `tg_worker` на отдельном VPS, НЕ там же, где API-ядро и БД.** Между `tg_worker` и ядром — внутренний HTTP API (см. §2.6a). В `tg_worker` нет ни БД, ни бакета — он stateless-адаптер, ровно по правилу 3 и §16 архитектуры.

- Рассмотренные варианты:
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **aiogram 3** (выбран) | async-first, активно развивается, большое русскоязычное комьюнити, встроенный FSM для многошаговых опросов, роутеры по тематике | неявно обязывает к своей архитектуре приложения, но правило 3 ограничивает её только папкой `app/adapters/telegram/` | ✓ |
  | python-telegram-bot (PTB) 21 | очень зрелая, подробная документация | PTB тянет собственный event-loop/queue; смешивать с нашим asyncio-воркером через SKIP LOCKED — лишние швы | нет |
  | aiohttp напрямую + Telegram Bot API | полный контроль | придётся самому писать парсинг Updates, FSM, валидацию типов — нет смысла в 2026-м | нет |
- Почему именно это под мою идею: aiogram 3 — скучный зрелый выбор для нового бота на Python, FSM решает «пошаговый опрос Бренд A/Бренд E» без своего велосипеда, и правило 3 оставляет его только в `app/adapters/telegram/bot.py` + `app/adapters/telegram/handlers/*` — ядро не знает про aiogram.
- Запасная альтернатива: python-telegram-bot 21 (если найдём проблему с aiogram, замена — переписать только адаптер).

### 2.4 База данных

**Выбрана: PostgreSQL 16** (уже стоит; выбор зафиксирован и обоснован в [03-база-данных.md](03-база-данных.md)).

- Альтернатива: MySQL 8 — тоже реляционная, тоже массовая, но партиальные индексы «работают не так, как в Postgres», `JSONB` беднее, `SELECT ... FOR UPDATE SKIP LOCKED` появился только в 8.0 и обвешан нюансами. Для нашей очереди на Postgres SKIP LOCKED и партиальных unique-индексов (слот → одна бронь, спин раз в день) — Postgres выигрывает.
- Почему именно это под мою идею: все 7 инвариантов из [03-база-данных.md §3](03-база-данных.md) опираются на partial unique index и `TIMESTAMPTZ`; плюс та же БД становится и брокером очереди ([04-потоки-данных.md §3](04-потоки-данных.md)) — один инфраструктурный компонент вместо двух.
- Запасная альтернатива: MySQL 8 (на крайний случай, если провайдер даёт managed MySQL дешевле managed Postgres — но на целевых провайдерах РФ оба есть).

### 2.5 ORM, миграции, валидация

**Выбран: SQLAlchemy 2 (async) + Alembic + Pydantic 2 + pydantic-settings** (уже стоят).

- ORM:
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **SQLAlchemy 2** (выбран) | SQL-ориентированный, честный async (`AsyncSession`), наиболее мощный в Python, работает с нашим `schema.sql` без обёрток | нужно читать документацию 2.0 (не 1.x) | ✓ |
  | SQLModel | удобно, Pydantic+SQLAlchemy в одном флаконе | обёртка над SA, часть сложных случаев требует «спуститься» в SA, экономия эстетическая | нет — проще не оборачивать |
  | Tortoise ORM / Piccolo | async-first, модели ближе к Django | меньше комьюнити, экзотика → жетон; слабее с partial unique index | нет |
- Миграции: **Alembic** — стандарт де-факто для SA, уже в `alembic.ini` и фазе 0. Альтернатив, которые не стоят жетона, нет.
- Валидация и настройки: **Pydantic 2 + pydantic-settings** — одна библиотека обслуживает и схемы входа/выхода, и парсинг `.env` в `app/config.py` (правило 5).
- Почему именно это под мою идею: сильный async-ORM обязателен (у нас всё асинхронно: FastAPI, aiogram, воркер SKIP LOCKED), SA 2 это даёт честно; Pydantic уже требуется FastAPI, добавить pydantic-settings — одна зависимость.
- Запасная альтернатива ORM: SQLModel (минимальная переработка, те же модели можно переобернуть).

### 2.6 Хостинг (где всё работает) — две разделённые роли

**Разделено на два контура:** ПДн-ядро — на одном РФ-сервере с БД и S3; messenger-воркеры (`tg_worker` и будущие `max_worker`, `whatsapp_worker`, `web_worker`) — на отдельных stateless-контейнерах. Это согласуется с правилом 4 из [00-правила-проекта.md](00-правила-проекта.md) и с существующей структурой docker-compose (`app`, `tg_worker` — уже разделены как сервисы в фазе 0).

**Контур 1 — ПДн-ядро (API + БД + S3).** Один РФ-провайдер, строго в РФ (152-ФЗ).

- **Выбран: Selectel** — VPS в РФ-регионе под API-ядро + Managed PostgreSQL (РФ) + Cloud Storage S3 (РФ).
- Рассмотренные варианты:
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **Selectel** (выбран) | дешёвый VPS от ~400 ₽/мес; есть Managed PostgreSQL РФ; S3-совместимый Cloud Storage в РФ; документация по 152-ФЗ; аттестованные зоны по требованию; API+БД+S3 — один кабинет | S3 называется Cloud Storage, при переносе на другого провайдера меняется endpoint — лечится адаптером (правило 4) | ✓ MVP |
  | Yandex Cloud | лучшая документация под 152-ФЗ, большой каталог сервисов (включая аттестованную зону), Managed PostgreSQL — зрелый | дороже Selectel для минимальной конфигурации в 1,5–3 раза, порог сложности выше | резерв |
  | VK Cloud | Managed PostgreSQL, S3 (Hotbox), РФ | меньше статей и готовых рецептов, у меня нет опыта | нет на MVP |
  | Timeweb Cloud | дёшево, VPS, S3 | нет managed Postgres на уровне Selectel/YC, при росте сам буду админить БД | резерв |
  | AWS / Hetzner / DigitalOcean | дёшево, зрело | **не РФ → нарушение 152-ФЗ для ПДн граждан РФ** | нельзя |
- Запасная альтернатива: **Yandex Cloud**.

**Контур 2 — messenger-воркеры (`tg_worker` и будущие).** Отдельные stateless-контейнеры, по одному на канал. **Для `tg_worker` — минимум две реплики за балансировщиком с первого дня** (защита от SPoF в день мероприятия, см. риск №1 в [09-риски.md](09-риски.md)): простой одного `tg_worker` в разгар ивента означает «бот замолчал на 3 часа у 5 стоек одновременно» — у продукта «один день ценности в месяц» второй попытки в тот же день нет.

- **Выбран: тот же Selectel, две VPS в разных зонах того же РФ-региона** (ниже сетевая задержка до API-ядра = 1–3 мс; та же учётка — один кабинет оплаты; разные зоны переживают падение одной машины и плановый ребут).
- **Балансировщик:** отдельный маленький VPS с Caddy (или Managed Load Balancer Selectel, когда появится в MVP-тарифе), на нём `setWebhook` в Telegram указывает на домен балансировщика. Балансировщик делает active health-check `/healthz` каждые 10 секунд, выводит нездоровую реплику из ротации без вмешательства человека. Алерт в тот же Telegram-канал (см. [06-внешние-сервисы.md §6](06-внешние-сервисы.md)) — при пропаже реплики > 60 секунд.
- Почему всё-таки РФ, а не любой зарубежный дешёвый VPS: сам факт `tg_worker` принимает телефон/имя/ник от Telegram и дальше передаёт их в API. Это момент «первичного получения ПДн оператором» — Роскомнадзор смотрит на это широко, безопаснее держать и воркеры в РФ, чтобы спор «считается ли это первичным сбором» вообще не возникал.
- При дальнейшем росте: добавление третьей реплики = ещё одна VPS в compose балансировщика; добавление MAX/WhatsApp = отдельная пара реплик с собственным балансировщиком, API-ядро остаётся одно.
- **Паспорт инфры мероприятия (см. §2.8 и риск №2 в [09-риски.md](09-риски.md)):** за 1 неделю до каждого мероприятия владелец заказывает временный upscale Managed PG и/или третью реплику `tg_worker` на день, после мероприятия — downscale. Расчёт тарифа — из нагрузочного теста фазы 10.

**Границы между контурами:**
- `tg_worker` **не ходит в Postgres напрямую**, не монтирует S3-бакет, не хранит на диске ни ПДн, ни токены гостей.
- Единственный исходящий канал `tg_worker` → ядро — внутренний HTTP API ядра (см. §2.6a).
- Если `tg_worker` упал — ядро работает (просто не доставляются сообщения в Telegram, задачи `telegram_send` остаются в `queued` и доедут при подъёме).
- Если ядро упало — `tg_worker` отвечает Telegram'у 5xx, Telegram ретранслирует вебхук (это нормальный путь, см. [04-потоки-данных.md §2](04-потоки-данных.md)).

**Деплой:** `docker compose up -d` на каждом VPS — скучнее некуда. Никакого Kubernetes в MVP (правило экономии жетонов). Backup Postgres — через Managed Backups Selectel + ночной `pg_dump` → S3 (это уже закреплено в [03-база-данных.md §5](03-база-данных.md), п. 9). Dev — docker-compose локально, оба сервиса на одной машине (прод-разделение воспроизводится только в staging).

### 2.6a Внутренний HTTP API ядра (для messenger-воркеров и админки)

Поскольку `tg_worker` живёт отдельно, нужен явный контракт.

- **Протокол:** HTTP/1.1 поверх TLS (Let's Encrypt), REST + JSON. gRPC сюда не оправдан — трафик умеренный, схем немного, overhead HTTP не критичен, зато отладка в разы проще.
- **Префикс маршрутов:** `/internal/v1/*` — отделён от `/admin/*` и будущих публичных путей. Через reverse-proxy (Caddy/nginx) эти маршруты закрыты по IP-allowlist (адреса VPS с messenger-воркерами) + mTLS **или** короткоживущий HMAC-подписанный токен в заголовке `X-Internal-Auth` (shared secret в env, ротация раз в N дней). Выбор между mTLS и HMAC — на фазе реализации, оба варианта описаны правилом 4 (адаптер + env), ядро принимает уже валидированный запрос.
- **Форма вызовов:** команда (команды use-case'ов ядра), а не CRUD. Пример (неполный):
  - `POST /internal/v1/channels/telegram/updates` — принять одно входящее от Telegram (`tg_worker` просто прокидывает Update, ядро само его разбирает и роутит на use-case);
  - `POST /internal/v1/channels/telegram/outbox/claim` — забрать пачку исходящих `telegram_send` задач из очереди (`tg_worker` поллит каждые 1–2 секунды или подписывается через Server-Sent Events — выбор на фазе реализации);
  - `POST /internal/v1/channels/telegram/outbox/ack` — подтвердить успешную/неуспешную отправку, ядро обновляет `jobs`.
- **Почему именно так:** `tg_worker` — чистый адаптер (правило 3): парсит Telegram → зовёт команду → рендерит ответ. Все инварианты (защита от дублей, выдача наград, consent-gate) живут в ядре, за одним API. Добавить MAX = поднять `max_worker` рядом, он дёргает те же команды под `POST /internal/v1/channels/max/updates`.
- **ПДн в этих запросах:** проходят по TLS внутри одной подсети провайдера; на диск у `tg_worker` не ложатся; в логи `tg_worker` маскируются тем же middleware, что в ядре (правило 2 — одна общая библиотека маскирования в `app/common/pii_mask.py`, подключается в обоих сервисах).
- **Альтернатива 1:** общая очередь (`tg_worker` ходит в Postgres напрямую) — отвергнута: тогда `tg_worker` знает про схему БД и ломает правило 3. Плюс сетевой доступ к БД надо открывать наружу, а это ослабляет контур ПДн.
- **Альтернатива 2:** gRPC — отвергнута как 0,5 жетона экзотики без выгоды на нашей нагрузке (десятки RPS).

### 2.7 Объектное хранилище (файлы: UGC-фото, Polaroid-результаты)

**Выбрано: Selectel Cloud Storage** (S3-совместимое, РФ-регион) в prod; **MinIO** локально в dev.

- Ограничение: ПДн-фото граждан РФ → хранилище в РФ (152-ФЗ).
- Рассмотренные варианты (все S3-совместимые):
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **Selectel Cloud Storage** (выбран) | тот же провайдер, что хостинг — один кабинет, одна точка оплаты; РФ-регион; дешёвый egress для соседнего VPS | — | ✓ |
  | Yandex Object Storage | лучшая совместимость с AWS SDK, зрелый | дороже, другой кабинет | резерв |
  | VK Cloud Hotbox | РФ, S3-совместимый | меньше опыта у комьюнити | нет на MVP |
  | AWS S3 / Cloudflare R2 / Backblaze B2 | топовые по цене/функциям | **не РФ → нельзя для ПДн** | нельзя |
  | «Самодельный MinIO на том же VPS» | бесплатно | теряется весь смысл managed-хранилища: бэкапы, HA, снапшоты, диск-квота — всё на мне | нет |
- Почему именно это под мою идею: ПДн-фото обязано лежать в РФ, у того же провайдера, что хостинг, — минимум трения; доступ наружу — через `/media/<id>` + presigned URL (это уже закреплено в [03-база-данных.md §4](03-база-данных.md) и [04-потоки-данных.md §4.5](04-потоки-данных.md)).
- Запасная альтернатива: **Yandex Object Storage**.
- Dev-окружение: MinIO в docker-compose — чтобы разрабатывать и писать тесты без похода в прод-бакет.

### 2.8 Очередь, фоновые и отложенные задачи

**Выбрано: собственный тонкий воркер поверх Postgres SKIP LOCKED (asyncio + SQLAlchemy)** — для очереди; **встроенный «тик каждую минуту» в том же воркере** — для шедулера (напоминания и авто-отмены записей, ночные батчи).

- Контракт поведения уже зафиксирован в [04-потоки-данных.md §3](04-потоки-данных.md): таблица `jobs`, `FOR UPDATE SKIP LOCKED`, `locked_until` с TTL 90с, 6 ретраев с экспоненциальным backoff, DLQ (`status='dead'`).
- Рассмотренные варианты:
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **Собственный воркер на SA 2 + asyncpg** (выбран) | ~150 строк кода; одна транзакция «создал Reward + поставил задачу»; никаких лишних демонов; реально скучно (SKIP LOCKED — встроенный Postgres) | свой код, не библиотека | ✓ полжетона |
  | **saq / arq** (запасная) | готовая очередь на Redis+asyncio, 2-строчный декоратор на задачу | ещё один демон (Redis), рассинхрон «добавил в Redis, транзакция откатилась» — классическая боль | нет для MVP (но готов адаптер — заменим без правок ядра) |
  | Celery + Redis | эталон для Python; большое комьюнити | sync-first, тяжёлый для нашей async-сцены, тот же Redis-рассинхрон, оверкилл для сотен задач в день | нет |
  | dramatiq + Redis | легче Celery, async есть | то же, плюс меньше комьюнити | нет |
  | **procrastinate** (запасная) | библиотека ровно для «очередь на Postgres SKIP LOCKED» для Python, тащит таблицу `jobs` и воркер | дополнительная зависимость, своя схема таблиц поверх моей, иногда ломает `alembic` | нет, но запомню как «готовый аналог моему велосипеду» |
- Шедулер (напоминания −5 мин и авто-отмена +5 мин для `appointments`, ночные батчи анонимизации и чистки):
  - **Выбран:** отдельная задача в том же воркере, пробуждается каждую минуту, делает SELECT из `appointments` и `jobs` по условиям из [04-потоки-данных.md §1.3](04-потоки-данных.md). «Таймеры» живут в БД как `remind_at`/`auto_cancel_at`, в памяти процесса их нет.
  - Альтернатива: **APScheduler**. Хорош для крона в памяти процесса, но у нас крон минималистичный (две запланированные пробежки в минуту), заводить ещё одну библиотеку с её timezone-гонками — лишнее.
- Почему именно это под мою идею: правило 3 из [00-правила-проекта.md](00-правила-проекта.md) запрещает «потерять джоб планировщика при рестарте». Любой подход с таймерами в памяти (APScheduler default, Celery beat без persist) эту гарантию ломает; подход «состояние в БД, воркер пробуждается SELECT'ом» — переживает рестарт без всякой магии.
- Запасная альтернатива: **procrastinate** (готовая Postgres-очередь, если своё решение внезапно упрётся во что-то).
- **Sizing пула — не угадываем, измеряем** (см. риск №2 в [09-риски.md](09-риски.md)). Числа «4 (dev) / 8 (prod)» — это стартовая гипотеза под нагрузку MVP «сотни задач в день»; реальная цифра для дня мероприятия берётся из нагрузочного теста фазы 10. Расчётный профиль пика (стартовая гипотеза, уточняется по данным первых двух мероприятий): до 500 одновременных активных гостей × 3 действия/мин = 25 RPS на вебхук + ~50 задач/мин в очереди + пик до 10 UGC-ingest параллельно. Паспорт инфры мероприятия (upscale Managed PG + 3-я реплика `tg_worker` + расширенный пул) — §2.6 выше, применяется за сутки до ивента.

### 2.13 Контейнеризация и оркестрация в MVP

**Выбрано: Docker + docker-compose на двух VPS** (по одному compose-файлу на каждый контур; уже стоит в фазе 0).

- VPS-1 (ПДн-ядро): `app` (FastAPI с публичным API, админкой и внутренним API) + локальный Caddy/nginx как reverse-proxy с TLS + подключение к Managed PostgreSQL и Cloud Storage.
- VPS-2 (messenger-воркер): `tg_worker` (aiogram 3) + локальный Caddy для вебхука Telegram с TLS. Больше ничего.
- Альтернативы:
  | Вариант | За | Против | Вердикт |
  |---|---|---|---|
  | **docker-compose × 2 VPS** (выбран) | ровно то, что мне нужно: простые сервисы в простых сетях; оба контура разворачиваются одной командой; при росте — просто ещё один `tg_worker`-VPS с тем же compose | не для многомашинной работы с динамическим скейлом | ✓ MVP |
  | Kubernetes (managed k8s у Selectel/YC) | «правильно» для прода | 2–3 жетона в один вечер, 0 выгоды на нагрузке MVP | нет |
  | Nomad / Docker Swarm | легче k8s | ещё одна экзотика без причины | нет |
  | Голый systemd на VPS | нулевая зависимость | скрытое состояние, сложнее воспроизводить локально | нет |
- Почему именно это под мою идею: `docker compose up -d` на каждом из двух VPS = деплой; разделение контуров — на уровне разных машин, а не разных кластеров.

### 2.14 CI

**Выбран: GitHub Actions** (уже заведён `.github/`).

- Альтернатива: GitLab CI — если переедем на GitLab, но пока репо на GitHub.
- Почему именно это под мою идею: репозиторий на GitHub, GHA бесплатен для публичных и щедр для приватных, YAML-формат — стандарт.

### 2.15 Тесты, линтеры, типы

**Выбраны: pytest + pytest-asyncio + httpx (как клиент к FastAPI в тестах) + freezegun + ruff + mypy** (уже стоят).

- Альтернатива для линтера: flake8+black+isort — три библиотеки вместо одной; ruff делает их работу в 20× быстрее.
- Альтернатива для типов: pyright — быстрее mypy, но mypy ближе к mainstream в Python-мире и строгий режим `app.core.*` уже настроен.
- Почему именно это под мою идею: ruff + mypy strict на `app/core/*` — минимум трения, максимум гарантий «ядро не ломается молча». pytest-asyncio нужен из-за асинхронного стека.

## 3. Три числа, которые смотрю каждый день

Это три числа, которые дают мне понять, что продукт работает, а инфра — здорова. Все три — SQL-запросы к Postgres, оформленные как `view` в БД + одна команда `psql`/мини-скрипт `python -m app.ops.daily`, который печатает их в консоль. Grafana/Prometheus — на MVP лишнее (это следующий шаг, не первый).

1. **Сколько гостей зарегистрировалось сегодня** (приняли согласие на ПДн, т. е. довели регистрацию до конца).
   - **Что меряем:** `SELECT COUNT(*) FROM consents WHERE accepted_at::date = current_date AND revoked_at IS NULL`.
   - **Почему именно это:** главный показатель, что продукт вообще жив и люди проходят вход; без регистрации нет ни одной активности.

2. **Сколько прохождений завершилось сегодня в разбивке по брендам** (из каких брендов идёт реальное взаимодействие, а какие стоят пустые).
   - **Что меряем:** `SELECT b.slug, COUNT(*) FROM attempts a JOIN activities act ON act.id=a.activity_id JOIN brands b ON b.id=act.brand_id WHERE a.finished_at::date = current_date AND a.status IN ('completed','approved') GROUP BY b.slug`.
   - **Почему именно это:** если Бренд A даёт 200 завершений, а Бренд C — 2, бренд Бренд C надо чинить (мало слотов, стойка пустая, никто не знает про QR), а не писать новые фичи.

3. **Сколько задач в карантине (DLQ) за последние 24 часа** (здоровье фонового пайплайна — не плодим ли мы «ошибку, которую никто не починит»).
   - **Что меряем:** `SELECT kind, COUNT(*) FROM jobs WHERE status='dead' AND updated_at >= now() - interval '24 hours' GROUP BY kind`.
   - **Почему именно это:** правила 00 запрещают «потерять джоб планировщика при рестарте», но ровно так же плохо — незаметно скопить 200 битых `telegram_send`. Если число > 0 — иду в `jobs.last_error`, разбираюсь. Если регулярно > 10 — что-то системно сломано.

## 4. Что я сознательно НЕ выбрал и почему (важнее списка «что выбрал»)

- **«Один VPS на всё» (API + БД + S3 + все messenger-воркеры в одном compose).** Отвергнут в пользу разделения ядро vs. messenger-воркер (см. §2.6): так и правило 4 из [00-правила-проекта.md](00-правила-проекта.md) про готовность к MAX/WhatsApp/веб выполняется физически (новый воркер = новый VPS, не трогая ядро), и падение одного адаптера не роняет остальных.
- **Микросервисы (разбиение ядра на сервисы по доменам: регистрация, модерация, награды, слоты и т. п.).** Решение для больших команд (3+ бэкендеров на домен) с разной скоростью релиза; у меня один разработчик и одно развёртывание ядра. Разделение «ядро vs. messenger-воркер» из §2.6 — это НЕ микросервисная архитектура, а чистое «ядро + адаптер» по правилу 3; ядро остаётся одним монолитом, модульность — через `app/core/` ↔ `app/adapters/`.
- **Kubernetes / Nomad / Docker Swarm на MVP.** 2–3 жетона потрачены впустую, 0 выгоды на 1 VPS и ≤ 1000 активных гостей на мероприятии. `docker compose up -d` — весь мой «оркестратор».
- **Redis / RabbitMQ / NATS как брокер очереди.** Ещё один демон, который может лечь независимо от БД, и классический рассинхрон «положил в брокер, транзакция откатилась». На нашей нагрузке (сотни задач в день) Postgres SKIP LOCKED справляется с 100×-ным запасом ([04-потоки-данных.md §3.4](04-потоки-данных.md)).
- **Celery.** Sync-first, тяжёлый, лишний брокер — выбран как антивыбор, см. выше.
- **Отдельный почтовый сервер / свой SMTP-демон.** Писем в MVP не отправляем (вся коммуникация — через Telegram). Если понадобится — Yandex Postmaster/Mail.ru/любой РФ-ESP, спрятанный за портом `app/core/ports/email.py`. Писать свой postfix — заведомо худшая идея.
- **Свой «AI-сервис» (локальная LLM на моём VPS).** VPS за 400 ₽/мес не вытянет LLM, а если и вытянет — я трачу внимание не туда. Когда AI понадобится — беру ЯGPT/GigaChat за адаптером (0,5–1 жетон, см. §2.9).
- **Своя S3 (MinIO на боевом VPS).** Теряется весь смысл managed-хранилища: бэкапы, HA, снапшоты, квоты, геораспределение. Managed S3 у Selectel — 1,5 ₽/ГБ в месяц, дешевле, чем мой час.
- **GraphQL-API, REST-клиент, SPA-админка.** 0 потребителей, 0 выгоды, недели работы, требующей фронтендера. Jinja+HTMX покрывает все 4 экрана админки (очередь UGC, расписание, выдача, лиды).
- **ORM с «автогенерацией миграций без ревью» (makemigrations авто-apply).** На проде миграции применяются только с явного разрешения владельца ([00-правила-проекта.md](00-правила-проекта.md) правило 7). Alembic написан руками + review.
- **ElasticSearch / ClickHouse / ML-пайплайны / отдельная BI-база.** На нагрузке «одно мероприятие в месяц, сотни гостей» это пустая аналитика. Три SQL-запроса (§3) печатаются из той же Postgres.
- **Keycloak / Auth0 / Firebase Auth для админки.** На 1–5 админов — Argon2id-хэш в `admin_users`, HTTPOnly cookie, CSRF double-submit (это уже закреплено правилом 10). Keycloak — целый отдельный демон, добавил бы 1 жетон.
- **MongoDB / DynamoDB / «NoSQL».** Данные у меня явно реляционные (гость ↔ прохождения ↔ награды с жёсткими уникальностями). JSONB в Postgres покрывает все несколько мест, где схема расходится ([03-база-данных.md §1](03-база-данных.md) и Журнал решений).
- **Платёжка в MVP.** Нет оплаты — нет платёжки (см. §2.10). Если появится — за портом, выбор провайдера РФ в тот момент, не сейчас.
- **SMS-провайдер.** Phone нужен нам только как контакт (152-ФЗ-согласованный), код подтверждения по SMS в MVP не отправляем (регистрация и так через Telegram, подтверждение идентичности — через `telegram_user_id`).

## 5. Внешние зависимости как «порты» (ядро не знает про вендора)

Правило 4 из [00-правила-проекта.md](00-правила-проекта.md): «любой внешний сервис — через сменный адаптер». Фиксирую список портов и их реализации под текущие вендоры. **Ядро импортирует только порт**, никогда — конкретный адаптер.

| Порт (`app/core/ports/`) | Что умеет (контракт) | Адаптер MVP (`app/adapters/`) | На что меняется |
|---|---|---|---|
| `messenger.py` | «отправить сообщение гостю X с текстом/кнопками/картинкой», «принять входящее сообщение», «ответить на callback»; идемпотентность по `(channel, external_id, update_id)`. **Адаптер живёт в отдельном сервисе `tg_worker` на отдельном VPS и ходит в ядро по внутреннему HTTP API (§2.6a)** | `telegram/` (aiogram 3) — отдельный контейнер на отдельном VPS | MAX, WhatsApp, веб-виджет — ещё один аналогичный контейнер (`max_worker`, `whatsapp_worker`, `web_worker`) + папка в `adapters/`, ядро не трогается |
| `internal_api_client.py` (на стороне `tg_worker`) | обёртка над `/internal/v1/*` ядра: `send_update(update) -> Response`, `claim_outbox(limit) -> jobs[]`, `ack(job_id, result)` | `internal_api_client/httpx_json.py` (asyncpg-независимый HTTPX-клиент с ретраями и HMAC/mTLS) | смена транспорта (gRPC и т. п.) — один файл |
| `object_storage.py` | `put(bucket, key, bytes, content_type) -> url`, `get(bucket, key) -> bytes`, `delete(bucket, key)`, `presigned_get(bucket, key, ttl) -> url` | `object_storage/selectel_s3.py` (boto3 с кастомным endpoint) + `object_storage/minio_dev.py` для dev | Yandex Object Storage / VK Hotbox — ещё один файл-адаптер, тот же интерфейс |
| `image_frame.py` | `apply(source_bytes, frame_slug) -> result_bytes` — наложить Polaroid-рамку | `image_frame/pillow.py` | pyvips, внешний AI-сервис — один новый адаптер |
| `password_hasher.py` | `hash(plain) -> hash`, `verify(plain, hash) -> bool` | `password/argon2.py` | bcrypt, Argon2id у провайдера — один адаптер |

| **(будущее)** `payment.py` | `create_invoice(amount_minor, currency, idem_key)`, `handle_webhook(payload) -> PaymentEvent` | — (не в MVP) | ЮKassa, Tinkoff, CloudPayments — один адаптер |

**Правило адаптера:** смена вендора = новый файл-адаптер + одна строка в `app/config.py` (выбор по env `MESSENGER_IMPL=telegram|max|whatsapp` и т. п.). **Ноль правок в `app/core/`**. Проверяется `grep -nE "from aiogram|import aiogram|boto3" app/core/` — должно быть пусто (правило 3).

**ИИ-адаптер отдельно.** Хотя ИИ в MVP нет, порт `app/core/ports/skin_analysis.py` *опишу заранее одним методом* (`analyze(image_bytes) -> SkinAnalysis`), чтобы при появлении модели я менял только один файл-адаптер, а не искал по кодовой базе места, где «ответы на опрос мапятся в рекомендации». Правило: ядро не знает слов «OpenAI», «YandexGPT», «GigaChat»; знает только `SkinAnalysisPort`.

## Журнал решений

- 2026-10-11 — **Главный выбор стека:** Python 3.12 + FastAPI 0.115 + aiogram 3 + SQLAlchemy 2 (async) + Alembic + PostgreSQL 16 + Selectel (VPS + Managed PG + Cloud Storage, РФ) + Jinja2/HTMX для админки + Postgres SKIP LOCKED как очередь + Pillow для Polaroid; ИИ и платежи — не в MVP, под порты. **Причина:** максимально скучный и зрелый набор, целиком соответствующий 152-ФЗ (хостинг и файлы в РФ), фазе 0 (ничего не ломаю из уже выбранного) и правилам 00 (headless-ядро, адаптеры для внешнего мира, состояние в БД, а не в памяти); потрачено 0,5 жетона экзотики из 3 (Postgres SKIP LOCKED вместо Redis-брокера), остальные 2,5 оставляю под AI и будущие платежи.
- 2026-10-11 — **Деплой разделён на два контура: ПДн-ядро (API+БД+S3) на одном РФ-VPS, messenger-воркер `tg_worker` на отдельном stateless-VPS**, оба — Selectel РФ, связь через внутренний HTTP API ядра (§2.6a). **Причина:** правило 4 из [00-правила-проекта.md](00-правила-проекта.md) требует архитектурной готовности к MAX/WhatsApp/веб-виджету — физическое разделение делает добавление нового канала операцией «поднять ещё один VPS с тем же compose», а не «пересобирать монолит»; при падении одного адаптера остальные живут; весь ПДн-store остаётся в одном контуре под одним кабинетом и 152-ФЗ.
- 2026-10-12 — /internal/v1/channels/telegram/updates расширен полем reply: {text, chat_id} | null — для синхронных ответов на простые команды до поднятия outbox; outbox остаётся каноном для всех фоновых реакций (notify_reward, напоминания, UGC-approve) — оркестратор, ADR-2 промта 2026-10-12-vertical-slice-impl.md (ссылка на запись в журнале 08).
- 2026-10-12 — **В зависимости добавлен `greenlet`** (отдельной строкой в `pyproject.toml` + `uv.lock`). **Причина:** `create_async_engine` SQLAlchemy 2 (выбор 2.5 выше, канон архитектуры) требует `greenlet` как обязательный транзитив при любом из драйверов `psycopg[binary]` / `asyncpg`; это не экзотика и 0 жетонов (греентред — чисто механический адаптер «sync-API SA ↔ async-event-loop»). Явно вписан в deps вместо экстры `sqlalchemy[asyncio]` — так явнее для ревьюера, что это одна конкретная зависимость, а не невидимый побочный эффект. Решение принято владельцем на вопрос исполнителя в промте 2026-10-12-vertical-slice-impl.md; альтернатива «перевести UoW+Repo на raw psycopg3 async без SQLAlchemy» отклонена — противоречит выбору 2.5 и ломает ORM-модели Окна 0.
- 2026-10-14 — **Jinja2 отложен до фазы 3; MVP-админка рендерится через stdlib `string.Template` в `app/admin/templating.py`.** FastAPI 0.143 транзитивно Jinja2 **не** тянет (в `uv.lock` его нет, `starlette.templating` падает `ImportError`); §2.2 выше про «идёт поставкой с FastAPI» для 0.143 — неточен, оставляю как исторический контекст. **Причина:** фаза 1.5 поднимает только 4 коротких шаблона (login, index, 404, 500) с автоэкранированием через `html.escape(quote=True)` + `SafeHtml`-маркер — stdlib хватает; XSS-пробы ревьюера показали нужное экранирование. Jinja2 (+ его условия/циклы/контекстное экранирование URL-атрибутов, валидация `post_url` по 07 §2.2а) войдёт в фазу 3 с реальными экранами модерации — там же разрешён `uv add jinja2` — оркестратор, ADR-11 ревью фазы 1.5 (2026-10-14-admin-skeleton-auth-review.md).
