# 03. База данных

Дата: 2026-10-11
Источник имён и смысла: [02-сущности.md](02-сущности.md). Правила и запреты: [00-правила-проекта.md](00-правила-проекта.md).

## СУБД и формат схемы

Выбор: **PostgreSQL 16**. Обоснование одной строкой: по фазе 0 уже заведён `docker-compose` с Postgres + `alembic`, нужны надёжные частичные уникальные индексы (bookable-слот → ровно одна активная бронь, «один спин в день»), `TIMESTAMPTZ` для таймлайнов напоминаний, `JSONB` для вариантов опроса и аудита без ПДн.

Формат схемы: переносимый `DDL` под Postgres в [schema.sql](schema.sql). Файл [schema.prisma](schema.prisma) трогать не буду — он остаётся заготовкой на случай смены стека. Как только [05-стек.md](05-стек.md) закроется (ожидаемо: Python + SQLAlchemy + Alembic), из `schema.sql` родятся модели в `app/db/models/` и первая миграция `alembic/versions/0001_initial.py`.

Логические разделы схемы:

- **core** — `users`, `consents`, `channel_accounts`;
- **catalog** — `brands`, `activities`, `survey_questions`, `product_recommendations`, `wheel_prizes`;
- **attempts** — `attempts` (главный агрегат) + его дочерние: `survey_answers`, `appointments`, `ugc_submissions`, `wheel_spins`, `frame_submissions`;
- **scheduling** — `slots`;
- **rewards** — `rewards`;
- **admin** — `admin_users`, `admin_brands`, `audit_log`.

## 1. Таблицы по-человечески

Общие правила ко всем таблицам (не повторяю ниже):

- У каждой строки — свой уникальный `id BIGSERIAL PRIMARY KEY`.
- У каждой таблицы есть `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` и `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()` (на `updated_at` висит триггер `set_updated_at`).
- Все ссылки между таблицами — настоящие внешние ключи, не «просто колонка с id».
- Все моменты времени — `TIMESTAMPTZ` в UTC; локальное время только на отображении.

Политика удаления указана у каждой таблицы одной строкой: **hard** (строка физически удаляется или ПДн-поля обнуляются насовсем), **soft** (ставим `deleted_at`/`revoked_at`/`cancelled_at`, из обычных запросов скрываем, в истории оставляем), **immutable** (запись не удаляется и не меняется — только дописывается).

### users — Гость

Один человек, подошедший к стойке. Поля:
- `first_name`, `last_name` (TEXT, NULL) — заполнены только если принято действующее согласие;
- `phone` (TEXT, NULL, уникален среди не-NULL) — только при согласии;
- `email` (TEXT, NULL, уникален среди не-NULL) — только при согласии;
- `registered_at` (TIMESTAMPTZ, NULL) — момент принятия первого согласия;
- `last_seen_at` (TIMESTAMPTZ, NULL) — последний контакт с ботом; обновляется при каждом входящем;
- `anonymized_at` (TIMESTAMPTZ, NULL) — выставлен, если гость сделал `/forget` или по политике хранения.

**Удаление: hard по ПДн / строка остаётся.** `/forget` обнуляет `first_name`, `last_name`, `phone`, `email`; строку не удаляем, иначе рассыпаются `attempts` и `rewards` для статистики (это закреплено в [02-сущности.md](02-сущности.md) и правиле 9 из [00-правила-проекта.md](00-правила-проекта.md)).

### consents — Согласие на обработку данных

Явное «да» по 152-ФЗ. На гостя — N строк (история версий).
- `user_id` (FK → users);
- `policy_version` (TEXT) — например `v1.2`;
- `text_hash` (TEXT, 64 hex) — SHA-256 текста политики на момент принятия;
- `accepted_at` (TIMESTAMPTZ);
- `revoked_at` (TIMESTAMPTZ, NULL) — пусто у действующих;
- `channel_type` (TEXT) — откуда принято (`telegram`, в будущем `max`, …).

**Удаление: immutable (append-only).** Запись никогда не меняется и не удаляется; отзыв = новая строка с `revoked_at` у прежней. Нужно, чтобы доказать в споре, что согласие было и было отозвано.

### channel_accounts — Привязка гостя к каналу

Отдельная вещь от `users`: один гость — N привязок (сегодня одна Telegram, завтра MAX/веб).
- `user_id` (FK → users);
- `channel_type` (TEXT) — `telegram` | `max` | `whatsapp` | `web`;
- `external_id` (TEXT) — `telegram_user_id`/аналог;
- `external_username` (TEXT, NULL) — ник в канале, тоже ПДн;
- `linked_at` (TIMESTAMPTZ);
- `unlinked_at` (TIMESTAMPTZ, NULL).

**Удаление: soft (`unlinked_at`).** Нужно для истории: откуда пришёл гость в прошлое мероприятие.

### brands — Бренд

Справочник из пяти брендов.
- `slug` (TEXT, уникален) — `brand_a`, `brand_b`, `brand_c`, `brand_d`, `brand_e`;
- `display_name` (TEXT), `tagline` (TEXT, NULL);
- `is_active` (BOOLEAN) — выключен на мероприятии;
- `deleted_at` (TIMESTAMPTZ, NULL).

**Удаление: soft.** История выдач по старому бренду должна читаться.

### activities — Активность

Шаблон сценария одного бренда.
- `brand_id` (FK → brands);
- `slug` (TEXT, уникален) — `brand_a_skin_survey`, `brand_c_stylist_booking`, …;
- `display_name` (TEXT);
- `kind` (TEXT) — `survey` | `booking` | `ugc` | `wheel` | `photo_frame` | `confirmation`;
- `is_active` (BOOLEAN), `deleted_at` (TIMESTAMPTZ, NULL);
- `limits` (JSONB) — настройки-ограничения (`{"max_per_day":1, "requires_moderation":true, "slot_window":"today"}`). JSONB здесь оправдан: эти ограничения читаются только use-case'ом конкретной активности, у них нет кросс-табличных запросов. При появлении устойчивых правил вытащу в отдельные колонки.

**Удаление: soft.**

### attempts — Прохождение (главный агрегат-владелец)

Один факт: гость X зашёл в активность Y. На нём держится всё — статус, награды, срок хранения.
- `user_id` (FK → users);
- `activity_id` (FK → activities);
- `channel_account_id` (FK → channel_accounts) — откуда зашёл; нужно для статистики по каналам;
- `status` (TEXT) — `in_progress` | `pending_moderation` | `approved` | `rejected` | `cancelled` | `completed` | `expired`;
- `started_at` (TIMESTAMPTZ NOT NULL DEFAULT now());
- `finished_at` (TIMESTAMPTZ, NULL);
- `summary` (TEXT, NULL) — одна строка для админки («кожа смешанного типа; промокод BIO-123»); **ПДн сюда не пишется** — только слаги/коды;
- `attempt_date` (DATE) — локальная дата старта в таймзоне мероприятия, нужна под уникальность «один раз в день» (см. горячий запрос №3);
- `expires_at` (TIMESTAMPTZ, NULL) — срок, после которого `in_progress` считается «брошен». Выставляется при вставке как `started_at + TTL_из_activities.limits.stale_ttl_minutes` (по умолчанию 120 минут). Нужен под джоб `expire_stale_attempts` (см. [04-потоки-данных.md §1.3](04-потоки-данных.md)), который переводит залипшие attempts в `expired` и освобождает partial unique «один раз в день» для следующих мероприятий (см. риск №5 в [09-риски.md](09-риски.md)). Индекс: `INDEX attempts_expire_due ON attempts (expires_at) WHERE status='in_progress'`.

**Удаление: soft через статусы (`cancelled` / `expired`).** Через `retention_days` (сейчас 90) батч чистит ПДн у `users`, сам `attempt` остаётся для агрегированной статистики — поля `summary` без ПДн, FK на `user_id` ведёт к анонимизированной строке.

### survey_questions — Вопрос опроса (шаблон)

- `activity_id` (FK → activities, kind='survey');
- `position` (INT) — порядковый номер в опросе;
- `text` (TEXT);
- `question_type` (TEXT) — `single_choice` | `multi_choice` | `free_text`;
- `options` (JSONB, NULL) — список вариантов `[{"key":"combo","label":"Смешанный"}, …]` для choice-типов.

**Удаление: soft (`deleted_at`).** Исторические ответы ссылаются на вопрос, редактировать его нельзя — новая версия заводится новой строкой.

### survey_answers — Ответ на вопрос

Дочь прохождения.
- `attempt_id` (FK → attempts);
- `question_id` (FK → survey_questions);
- `selected_option_keys` (JSONB, NULL) — список выбранных ключей для choice;
- `free_text` (TEXT, NULL) — для free_text;
- `answered_at` (TIMESTAMPTZ).

**Удаление: hard при `/forget` гостя.** Это непрямые ПДн (ответы о коже/настроении), поэтому удаляется вместе с анонимизацией.

### product_recommendations — Карточка рекомендованного продукта (справочник)

- `activity_id` (FK → activities);
- `condition` (JSONB) — простое правило `{"skin_type":"combo"}` или `{"mood":"calm"}`;
- `product_name` (TEXT), `caption` (TEXT, NULL);
- `product_url` (TEXT);
- `position` (INT);
- `is_active` (BOOLEAN), `deleted_at` (TIMESTAMPTZ, NULL).

**Удаление: soft.** Выданный набор хранит только id карточек (`rewards.product_recommendation_ids`, ADR-14): soft-удалённая карточка остаётся в истории гостя, а её название, подпись и URL читаются из справочника. Отдельной копии набора не сохраняем.

### slots — Слот записи

- `activity_id` (FK → activities, kind='booking');
- `start_at` (TIMESTAMPTZ);
- `duration_minutes` (SMALLINT) — 15 у Бренд C; у Бренд A — тоже слоты сегодняшнего дня;
- `kind` (TEXT) — `bookable` | `break`;
- `deleted_at` (TIMESTAMPTZ, NULL).

Поля «занят или нет» в самой таблице нет: это производное от `appointments`, и держать его явно — риск рассинхрона. Занятость считается в запросе через `LEFT JOIN appointments ... WHERE a.id IS NULL`.

**Удаление: soft.**

### appointments — Запись к эксперту (бронь слота)

Дочь прохождения `kind='booking'`.
- `attempt_id` (FK → attempts);
- `slot_id` (FK → slots);
- `status` (TEXT) — `booked` | `reminded` | `arrived` | `late` | `cancelled_by_user` | `cancelled_auto`;
- `remind_at` (TIMESTAMPTZ) — слот минус 5 минут;
- `auto_cancel_at` (TIMESTAMPTZ) — слот плюс 5 минут;
- `reminded_at` (TIMESTAMPTZ, NULL) — проставляет джоб напоминания;
- `arrived_at` (TIMESTAMPTZ, NULL);
- `arrived_marked_by_admin_id` (FK → admin_users, NULL);
- `cancelled_at` (TIMESTAMPTZ, NULL).

**Удаление: нет (immutable по статусу).** Отмена — не DELETE, а переход в `cancelled_*`.

### ugc_submissions — Фото + ссылка на пост от гостя

Дочь прохождения `kind='ugc'`.
- `attempt_id` (FK → attempts);
- `file_bucket` (TEXT), `file_key` (TEXT), `file_content_type` (TEXT), `file_size_bytes` (BIGINT) — ссылка на объектное хранилище; **в БД самого файла нет**;
- `post_url` (TEXT, NULL);
- `status` (TEXT) — `pending` | `approved` | `rejected`;
- `rejection_reason_slug` (TEXT, NULL), `rejection_note` (TEXT, NULL);
- `decided_by_admin_id` (FK → admin_users, NULL);
- `submitted_at` (TIMESTAMPTZ), `decided_at` (TIMESTAMPTZ, NULL).

**Удаление: hard при `/forget` гостя.** Файл в хранилище удаляется параллельно (это тоже ПДн).

### wheel_prizes — Приз колеса (справочник)

- `activity_id` (FK → activities, kind='wheel');
- `title` (TEXT);
- `prize_kind` (TEXT) — `mini_gift` | `compliment` | `promocode`;
- `weight` (INT, > 0) — вес вероятности в целых единицах; нормируется в коде;
- `stock_left` (INT, NULL) — остаток; `NULL` = бесконечный;
- `is_active` (BOOLEAN), `deleted_at` (TIMESTAMPTZ, NULL).

**Удаление: soft.** История выпавших призов ссылается сюда.

### wheel_spins — Факт вращения

Дочь прохождения `kind='wheel'`.
- `attempt_id` (FK → attempts);
- `wheel_prize_id` (FK → wheel_prizes);
- `spun_at` (TIMESTAMPTZ);
- `spin_date` (DATE) — локальная дата вращения; нужна под уникальность «один спин в день».

**Удаление: immutable.** Факт выдачи, не трогается.

### frame_submissions — Polaroid-рамка

Дочь прохождения `kind='photo_frame'`. Может быть несколько (повторная обработка).
- `attempt_id` (FK → attempts);
- `source_bucket`, `source_key`, `source_content_type`, `source_size_bytes` — исходник;
- `result_bucket`, `result_key`, `result_content_type`, `result_size_bytes` — результат (NULL до готовности);
- `status` (TEXT) — `queued` | `done` | `failed`;
- `failure_reason` (TEXT, NULL);
- `completed_at` (TIMESTAMPTZ, NULL).

**Удаление: hard при `/forget`.** Оба файла удаляются из хранилища.

### rewards — Награда (второй рабочий кирпич)

Единый тип на всё, что выдаётся гостю.
- `attempt_id` (FK → attempts);
- `reward_type` (TEXT) — `promocode` | `voucher` | `physical_gift` | `recommendation_set` | `leaflet` | `wheel_prize`;
- `code` (TEXT, NULL, уникален среди не-NULL) — для `promocode`/`voucher`; у остальных NULL;
- `product_recommendation_ids` (JSONB, NULL) — для `recommendation_set`: snapshot ids на момент выдачи;
- `wheel_prize_id` (FK → wheel_prizes, NULL) — для `wheel_prize`;
- `title` (TEXT, NULL) — короткое название для `physical_gift`/`leaflet`;
- `issued_at` (TIMESTAMPTZ);
- `redeemed_at` (TIMESTAMPTZ, NULL) — когда погашена у стойки (для `voucher`/`physical_gift`);
- `redeemed_by_admin_id` (FK → admin_users, NULL);
- `revoked_at` (TIMESTAMPTZ, NULL), `revoke_reason` (TEXT, NULL) — для «отозвать награду»;
- `expires_at` (TIMESTAMPTZ, NULL) — опционально; `NULL` = не истекает (пока вопрос «гасим ли мы сами просроченные промокоды» открыт в [02-сущности.md](02-сущности.md), держу поле заранее);
- `is_bearer` (BOOLEAN NOT NULL) — `true` для предъявительских (`promocode` на сайт), `false` для именных (`voucher`, `physical_gift`, именной `wheel_prize`). По умолчанию выводится из `reward_type` при вставке (`promocode` → true, `voucher`/`physical_gift` → false, `wheel_prize` → по `prize_kind`); колонка явная, чтобы правило было прочитано базой, а не угадано кодом;
- `redeem_otp` (TEXT, NULL), `redeem_otp_expires_at` (TIMESTAMPTZ, NULL) — одноразовый код для именных наград (см. [02-сущности.md §7](02-сущности.md) и риск №3 в [09-риски.md](09-риски.md)); у предъявительских оба поля NULL. CHECK: `(is_bearer AND redeem_otp IS NULL) OR (NOT is_bearer)`; при каждом нажатии гостя «подойду сейчас» OTP пересоздаётся с новым сроком жизни ~5 минут. Погашение `UPDATE rewards SET redeemed_at=now(), redeemed_by_admin_id=$1 WHERE id=$2 AND is_bearer=false AND redeem_otp=$3 AND redeem_otp_expires_at > now() AND redeemed_at IS NULL` — если 0 строк затронуто, админу «код не найден или просрочен». Партиальный индекс `UNIQUE INDEX rewards_active_otp ON rewards (redeem_otp) WHERE redeem_otp IS NOT NULL AND redeemed_at IS NULL` — защита от совпадения двух живых OTP.

**Удаление: soft (`revoked_at`).** Награду не удаляем — иначе рушится аудит выдачи у стойки.

### admin_users — Сотрудник

- `login` (TEXT, уникален);
- `password_hash` (TEXT) — Argon2id;
- `display_name` (TEXT);
- `is_active` (BOOLEAN);
- `last_login_at` (TIMESTAMPTZ, NULL);
- `deleted_at` (TIMESTAMPTZ, NULL).

**Удаление: soft.** На сотрудника ссылаются `decided_by_admin_id`, `redeemed_by_admin_id`, `arrived_marked_by_admin_id` — физически удалить = потерять аудит.

### admin_brands — Связь «сотрудник ↔ бренд» (M:N)

- `admin_id` (FK → admin_users);
- `brand_id` (FK → brands);
- `granted_at` (TIMESTAMPTZ);
- Первичный ключ — пара `(admin_id, brand_id)`.

**Удаление: hard** (просто снимаем доступ).

### audit_log — Журнал чувствительных действий

- `actor_admin_id` (FK → admin_users, NULL);
- `actor_user_id` (FK → users, NULL) — ровно одно из двух не-NULL (CHECK);
- `action` (TEXT) — `view_full_phone` | `approve_ugc` | `reject_ugc` | `redeem_reward` | `revoke_consent` | `anonymize_user` | `jobs_dead_revive` | `jobs_dead_bury` | …;
- `object_type` (TEXT), `object_id` (BIGINT) — полиморфная ссылка (`users`/`ugc_submissions`/`rewards`/`consents`/`jobs`); CHECK расширен миграцией 0020 (фаза 10b-2).
- `occurred_at` (TIMESTAMPTZ NOT NULL DEFAULT now());
- `details` (JSONB, NULL) — короткие детали, **без ПДн** (это закреплено правилом 2).

**Удаление: immutable.** Append-only, никогда не чистится.

## 2. Горячие запросы и индексы под них

Сначала сами запросы, которые будут крутиться постоянно; индексы — ровно под них, не наугад.

**Q1. «Распознать гостя по Telegram-ID на каждое входящее сообщение».** Бот получает каждое сообщение → первым делом `SELECT user_id FROM channel_accounts WHERE channel_type='telegram' AND external_id=$1 AND unlinked_at IS NULL`. Самый частый запрос всего продукта.
→ `UNIQUE INDEX channel_accounts_lookup ON channel_accounts (channel_type, external_id) WHERE unlinked_at IS NULL`.

**Q2. «Есть ли у гостя действующее согласие текущей версии?»** Перед любой записью ПДн: `SELECT 1 FROM consents WHERE user_id=$1 AND policy_version=$2 AND revoked_at IS NULL`.
→ `UNIQUE INDEX consents_active ON consents (user_id, policy_version) WHERE revoked_at IS NULL` — заодно гарантирует «у гостя не бывает двух действующих согласий одной версии».

**Q3. «Проходил ли гость активность сегодня?» (анти-повтор).** При старте активности проверяем: `SELECT 1 FROM attempts WHERE user_id=$1 AND activity_id=$2 AND attempt_date=current_date AND status NOT IN ('cancelled','expired')`. (ADR-19, фаза 3a: `rejected` занимает день, иначе лимит повторов обходится новым стартом.)
→ `UNIQUE INDEX attempts_once_per_day ON attempts (user_id, activity_id, attempt_date) WHERE status IN ('in_progress','pending_moderation','approved','completed','rejected')` — это *одновременно* индекс для чтения и ограничение целостности («база сама не даст создать второй»).
→ плюс обычный `INDEX attempts_user_recent ON attempts (user_id, started_at DESC)` под экран «вся история гостя».

**Q4. «Мои промокоды и ваучеры».** Гость жмёт кнопку → `SELECT r.* FROM rewards r JOIN attempts a ON r.attempt_id=a.id WHERE a.user_id=$1 AND r.revoked_at IS NULL AND r.reward_type IN ('promocode','voucher') AND (r.expires_at IS NULL OR r.expires_at > now()) ORDER BY r.issued_at DESC`.
→ `INDEX attempts_user ON attempts (user_id)` + `INDEX rewards_attempt ON rewards (attempt_id)` + `INDEX rewards_active_codes ON rewards (reward_type, issued_at DESC) WHERE revoked_at IS NULL AND code IS NOT NULL`.

**Q5. «Очередь модерации UGC для сотрудника бренда X».** Админ открыл очередь: `SELECT u.* FROM ugc_submissions u JOIN attempts a ON a.id=u.attempt_id JOIN activities act ON act.id=a.activity_id WHERE u.status='pending' AND act.brand_id=$1 ORDER BY u.submitted_at ASC`.
→ `INDEX ugc_pending ON ugc_submissions (submitted_at) WHERE status='pending'` + `INDEX attempts_activity ON attempts (activity_id)` (для фильтра по бренду через activity).

**Q6. «Свободные слоты сегодня для активности X».** Гость выбирает время: `SELECT s.* FROM slots s LEFT JOIN appointments a ON a.slot_id=s.id AND a.status IN ('booked','reminded','arrived') WHERE s.activity_id=$1 AND s.kind='bookable' AND s.deleted_at IS NULL AND s.start_at::date=current_date AND a.id IS NULL ORDER BY s.start_at`.
→ `INDEX slots_bookable_by_activity ON slots (activity_id, start_at) WHERE kind='bookable' AND deleted_at IS NULL`.
→ **Критичный унику**: `UNIQUE INDEX appointments_slot_active ON appointments (slot_id) WHERE status IN ('booked','reminded','arrived')` — ровно одна активная бронь на слот; это ключевая гарантия целостности для записи к эксперту.

**Q7. «Джоб планировщика: кому напомнить и кого авто-отменить».** Каждую минуту: `SELECT * FROM appointments WHERE status='booked' AND remind_at <= now() AND reminded_at IS NULL`; плюс `SELECT * FROM appointments WHERE status IN ('booked','reminded') AND auto_cancel_at <= now() AND arrived_at IS NULL`.
→ `INDEX appointments_remind_due ON appointments (remind_at) WHERE status='booked' AND reminded_at IS NULL`.
→ `INDEX appointments_cancel_due ON appointments (auto_cancel_at) WHERE status IN ('booked','reminded') AND arrived_at IS NULL`.

**Q8. «Чистка устаревших прохождений» (батч-джоб раз в сутки).** `SELECT user_id FROM attempts WHERE created_at < now() - interval '90 days' GROUP BY user_id` → анонимизация гостей, которые не возвращались.
→ `INDEX attempts_old ON attempts (started_at)` — одного обычного btree достаточно: батч идёт раз в сутки, scan допустим; городить partial индекс не оправдано.

Остальные FK индексируются стандартно (`CREATE INDEX ... ON child (parent_id)`) — Postgres не делает это автоматически.

Чего я **не** индексирую: `summary` в attempts (не ищем по нему), `details` в audit_log (поиск ad-hoc, редкий — JSONB-индекс добавим, когда появится рутинный запрос), `title`/`display_name` справочников (редкие полнотекстовые нужды).

## 3. Инварианты (что база не даст нарушить)

- **Ссылочная целостность**: все FK — настоящие. Удаление родителя с живыми детьми запрещено (`ON DELETE RESTRICT`), кроме `admin_brands` → `admin_users`/`brands` (там `ON DELETE CASCADE` — это чистая M:N-связь без собственных данных).
- **Уникальный id** у каждой строки (`BIGSERIAL PRIMARY KEY`), везде.
- **`created_at` / `updated_at`** у каждой таблицы; `updated_at` ведёт триггер `set_updated_at()`.
- **Удалённое не возвращается в обычных запросах**: везде, где есть `deleted_at` / `revoked_at` / `cancelled_at`, use-case'ы ставят фильтр `IS NULL`; для частых случаев рядом стоит частичный индекс `WHERE ... IS NULL`.
- **Один слот — одна активная бронь** (Q6).
- **Один спин колеса в день на гостя**: `UNIQUE INDEX wheel_spins_once_per_day ON wheel_spins ((attempt→user_id), (attempt→activity_id), spin_date)` — реализуется через денормализацию `user_id` и `activity_id` в саму `wheel_spins`, иначе унику по полю через JOIN не повесить. См. DDL ниже.
- **Один набор ПДн — один гость**: `UNIQUE INDEX users_phone ON users (phone) WHERE phone IS NOT NULL`, аналогично email.
- **Нет двух действующих согласий одной версии у одного гостя** (Q2).
- **Анти-дубль-выдача награды**: `UNIQUE INDEX rewards_per_attempt_type ON rewards (attempt_id, reward_type)` — на один attempt один раз каждый тип награды (Бренд A даёт `recommendation_set` + `promocode` — разные типы, лимит выполняется; Бренд B даёт `voucher` + `promocode` — то же). Если появятся сценарии «две разных по смыслу награды одного типа», унику расширю до `(attempt_id, reward_type, grant_slug)`.
- **Промокод и ваучер — глобально уникальны**: `UNIQUE INDEX rewards_code ON rewards (code) WHERE code IS NOT NULL` — повторный вход того же кода (например, при двойной обработке события выдачи) не создаст вторую проводку. **Это аналог «один внешний идентификатор платежа — ровно одна проводка»**, перенесённый на наш не-платёжный домен: деньги у нас не ходят, но код награды — тот же единственный «внешний идентификатор», по которому вторая запись должна быть отклонена базой, а не кодом.
- **Актёр аудита — либо админ, либо гость, но не оба и не никто**: `CHECK ((actor_admin_id IS NOT NULL) <> (actor_user_id IS NOT NULL))`.
- **`attempt_date` соответствует `started_at`**: `CHECK (attempt_date = (started_at AT TIME ZONE 'Europe/Moscow')::date)`.
- **`finished_at >= started_at`** — где заполнен; аналогично `redeemed_at >= issued_at`, `revoked_at >= issued_at`, `auto_cancel_at > remind_at > slot.start_at - 10 min` (последнее — через триггер при вставке, а не CHECK, т.к. включает чужую таблицу).

### Политика удаления — осознанно по таблицам

| Таблица | Режим | Обоснование |
|---|---|---|
| `users` | **hard по ПДн** (поля NULL, строка остаётся) | `/forget` стирает имя/тел/почту; строка нужна для статистики без ПДн |
| `consents` | **immutable** (append-only) | Доказательство принятия и отзыва |
| `channel_accounts` | **soft** (`unlinked_at`) | История, из какого канала гость был в прошлое мероприятие |
| `brands`, `activities`, `product_recommendations`, `slots`, `wheel_prizes`, `survey_questions` | **soft** (`deleted_at`) | На них ссылаются исторические attempts/rewards |
| `attempts` | **soft через статус** (`cancelled`/`expired`) | Чистится через анонимизацию ПДн у `users`, сама строка — бизнес-факт |
| `survey_answers`, `ugc_submissions`, `frame_submissions` | **hard при `/forget`** | Это непрямые ПДн: ответы, фото лица |
| `appointments`, `wheel_spins` | **immutable по статусу** | Отмена — это статус, не DELETE |
| `rewards` | **soft** (`revoked_at`) | Выданное не удаляется, только помечается отозванным |
| `admin_users` | **soft** (`deleted_at`) | На сотрудника ссылается аудит выдачи |
| `admin_brands` | **hard** | Чистая связка, без своих данных |
| `audit_log` | **immutable** | Append-only, не чистится |

### О деньгах

Реальных платежей в MVP нет (это зафиксировано в правиле проекта «потеря/дубль/подмена промокода считается инцидентом»). Если платежи появятся — суммы будут храниться **только** целым числом в минимальных единицах (`BIGINT amount_minor` + `CHAR(3) currency`), никаких `NUMERIC`/`FLOAT`; одна проводка (`payments`) по уникальному `provider_payment_id` (`UNIQUE INDEX payments_provider_id ON payments (provider_payment_id)`), чтобы повторный вебхук платёжки не списал второй раз. Пока же этот принцип применён к единственному «внешнему идентификатору» нашего домена — коду промокода/ваучера (см. выше `rewards_code`).

## 4. Файлы

UGC-фото гостей и обработанные Polaroid-кадры — большие бинарники; в БД их не кладём.

- **Хранилище**: S3-совместимый бакет (локальный MinIO в dev; у заказчика на выборе — Yandex Object Storage / S3 / свой MinIO).
- **В БД (`ugc_submissions`, `frame_submissions`)**: `*_bucket`, `*_key`, `*_content_type`, `*_size_bytes`. Никаких `BYTEA` с содержимым файла.
- **Доступ**: админка и бот отдают файлы через свой же `/media/<id>` (правило 9: ПДн — только на нашем сервере), под капотом — presigned URL с коротким TTL. Напрямую бакет наружу не публикуем.
- **Удаление файла идёт в паре с удалением строки**: при `/forget` гостя или отклонении UGC старше N дней use-case удаляет и строку, и объект в бакете (two-phase: сначала БД, потом бакет; при сбое второго шага остаётся «сирота» в бакете — чистится ночным job'ом по diff'у).

## 5. Как менять базу позже без потерь

Миграции — Alembic (уже стоит с фазы 0). Правила:

1. **Каждое изменение — отдельная ревизия со своей датой** в `alembic/versions/`. Имя: `YYYYMMDD_HHMM_<slug>.py`.
2. **У каждой ревизии есть `downgrade()`** — хотя бы на уровне обратного DDL. На проде мы его не запускаем (откат делается forward-fix'ом), но на dev-ветках `downgrade -1` экономит часы.
3. **Применённую на проде ревизию никогда не редактируем.** Если ошиблись — новая ревизия поверх.
4. **Удаление поля с живыми данными — в два шага:**
   - шаг 1: приложение перестаёт писать и читать поле; поле становится `NULL`able, если ещё не было; выкатываем;
   - шаг 2 (отдельной ревизией, не раньше следующей выкатки): `ALTER TABLE ... DROP COLUMN`.
5. **Переименование — в три шага:** добавить новую колонку → двойная запись в приложении → удалить старую. На любом промежуточном шаге прод работает.
6. **Создание индекса на боевой таблице — только `CONCURRENTLY`** (отдельной ревизией без транзакции).
7. **Сиды** (`brands`, стартовые `activities`, `survey_questions`, `product_recommendations`, стартовые `wheel_prizes`) — отдельными миграциями `alembic/versions/*_seed_*.py`, idempotent (`ON CONFLICT (slug) DO NOTHING`). Это гарантирует правило 5 из [00-правила-проекта.md](00-правила-проекта.md): названия брендов и слаги живут в БД, а не в коде.
8. **Не оптимизируем под объёмы, которых нет.** Партиционирование `attempts`/`audit_log` — только когда реально разрастётся до десятков миллионов строк; сейчас лишнее.
9. **Бэкапы**: ежедневный `pg_dump` → S3, retention 30 дней. Перед `alembic upgrade head` на проде — ручной `pg_dump` + подтверждение владельца (это правило 7).

- 2026-10-11 — **ПДн-поля `users.first_name/last_name/phone/email` — nullable.** Это прямое следствие правила 1 (запись ПДн — только после consent): пока consent не принят, строка `users` может уже существовать (создана при первом сообщении), но ПДн-поля пусты.
