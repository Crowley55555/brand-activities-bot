## О чём этот файл

Куда ляжет каждый кусок кода, у кого одна дверь, кто кого может звать, какие дочерние таблицы живут внутри модуля своего агрегата, и как разделить всё это между несколькими параллельными окнами Claude так, чтобы они не лезли в одни и те же файлы.

Пять принципов (как закон, не повторяю ниже в каждой секции):

1. **Вертикальные срезы по активностям** (`core/activities/<kind>/` — одна активность целиком в одной папке) **+ горизонтальные слои** (`api/` и `admin/` → `core/*/` → `core/ports/*` → `adapters/*` → `workers/` → `db/`).
2. **Один файл — одна ответственность.** Новая возможность — новый файл, а не разрастание старого.
3. **Одна входная дверь (`__init__.py`).** Снаружи модуля ходят только через то, что экспортировано в `__init__.py` этого модуля; внутрь напрямую — нельзя.
4. **Зависимости строго вниз.** Домен (`core/`) никогда не импортирует адаптеры (`adapters/`), aiogram, boto3, SQLAlchemy. Домен объявляет **порты** (`core/ports/*.py`), адаптеры их реализуют.
5. **Каждый внешний сервис — за адаптером** в `adapters/<kind>/<vendor>.py`. Имя вендора (`selectel_s3`, `argon2`, `pillow`, `telegram_webhook`) живёт только там.

## 1. Варианты раскладки, которые я рассмотрел

### Вариант А — чисто горизонтальные слои (отвергнут)

`routers/`, `services/`, `repositories/`, `schemas/` на верхнем уровне, активности растёрты по всем папкам.

- За: привычно, легко завести.
- Против: нельзя сказать «вот папка `wheel/` — вся логика колеса здесь». «Запись к стилисту» размазана на 4 папки, окно Claude, которому поручили её, лезет в чужие файлы. Правило 1 (вертикальный срез) нарушается первым же модулем.

### Вариант Б — вертикальные срезы по активностям + общие горизонтальные слои (выбран)

`core/activities/survey/`, `core/activities/booking/`, `core/activities/ugc/`, `core/activities/wheel/`, `core/activities/photo_frame/`, `core/activities/confirmation/` — каждая активность целиком в своей папке. Параллельно — общие модули-«кирпичи» (`core/users/`, `core/consent/`, `core/channels/`, `core/catalog/`, `core/attempts/`, `core/rewards/`, `core/jobs/`, `core/admin_access/`, `core/audit/`, `core/moderation_queue/`, `core/personal_data/`, `core/media/`). Снаружи ядра — тонкие слои `api/` (HTTP), `admin/` (Jinja+HTMX), `adapters/` (внешний мир), `workers/` (фоновые задачи), `db/` (ORM+миграции).

- За: одна активность = одна папка = одно окно Claude = одна зона ответственности. Общие вещи (`users`, `rewards`, `jobs`) не копипастятся — они лежат отдельно, активности зовут их через `__init__.py`. Шестая активность в будущем = новая папка в `core/activities/`, остальное не трогается.
- Против: сначала надо аккуратно договориться, что лежит «в активности», а что — «в общем кирпиче» (`Reward`, `Attempt`, `jobs`). Описано в §2 ниже, граница зафиксирована.

### Вариант В — микросервисы (разбить ядро на отдельные сервисы) (отвергнут)

Прямо запрещён последней строкой промта и уже отвергнут в [05-стек.md §4](05-стек.md). Один деплой ядра. Разделение «ПДн-ядро vs. `tg_worker`» (§2.6 из [05-стек.md](05-стек.md)) — это не микросервисы, а «ядро + адаптер»: `tg_worker` живёт в этом же репо, но запускается отдельным контейнером.

### Почему именно Вариант Б — простыми словами

Представьте пять витрин в одном магазине: Бренд A, Бренд B, Бренд C, Бренд D, Бренд E. Общие кассы (`users`, `consent`, `rewards`), общая касса приёма товаров (`attempts`), общая очередь курьеров (`jobs`), общие камеры наблюдения (`audit`) — одни на весь магазин, лежат в своих служебных помещениях. Но витрина Бренд D со своим колесом подарков — целиком в одном помещении: её можно переделать, не трогая другие витрины. Шестая витрина в будущем — поставим ещё одно помещение, кассу и курьеров не меняем.

## 4. Контракты на границах модулей

Это главное: что одна часть передаёт другой и в каком виде. Форма данных — маленькие `dataclass`/`Pydantic`-модели в `core/types/dto.py` и `core/types/results.py`. Контракт меняется только осознанно, записью в журнал решений; изменивший обязан обновить обе стороны границы.

Общий формат: **команда** принимает `*Id` (или `*Ref`), возвращает `*Result` (или бросает `ValidationError`/`ConflictError`/`NotFound`/`Forbidden`). ПДн в DTO не передаются, кроме явных команд обновления ПДн.

### 4.1 Границы между модулями ядра

| Граница | Команда (вход → выход) | Ошибки, которые ядро имеет право бросить |
|---|---|---|
| `channels` → `users` | `lookup_user(channel_type, external_id) -> UserRef \| None`; `link(user_id, channel_type, external_id, external_username) -> ChannelRef` | `NotFound` |
| `consent` → `users` | `has_active_consent(user_id) -> bool`; `accept(user_id, channel_type) -> ConsentRef`; `revoke(user_id, reason) -> None` | — |
| `users` ← любой модуль | `require_consent(user_id)` — guard; при отсутствии действующего `Consent` бросает `ConflictError("consent_required")` → `api` рендерит 409 (правило 1) | `ConflictError` |
| `attempts` → `catalog`, `users`, `channels` | `start_attempt(user_id, activity_slug, channel_account_id) -> StartAttemptResult(attempt_id, status, kind, next_step_payload)` — ВНУТРИ транзакции делает: consent-check, once-per-day-check, insert attempt | `ConflictError("already_passed_today")`, `ConflictError("consent_required")`, `NotFound` |
| `attempts` → любой `activities.*` | `close_attempt(attempt_id, status: Terminal, summary) -> AttemptRef` — одной транзакцией; переход `in_progress → completed/approved/rejected` атомарный `UPDATE ... WHERE status='in_progress'` | `ConflictError("already_closed")` |
| `activities.* → rewards` | `grant_on_completion(attempt_id, grants: list[GrantSpec]) -> list[RewardIssued]` — вызывается ИЗ ТОЙ ЖЕ транзакции, что `close_attempt`. `GrantSpec = {reward_type, title?, product_recommendation_ids?, wheel_prize_id?, code_template?}` | `ConflictError("duplicate_grant")` (из unique `(attempt_id, reward_type)`) |
| `rewards` → `jobs` (outbox) | После commit'а — `jobs.enqueue(kind='notify_reward', payload={reward_id}, idempotency_key=f'reward_notice:{reward_id}')` | — |
| `activities.booking` → `jobs` | При `book_slot`: `jobs.enqueue(kind='notify_appointment_reminder', payload={appointment_id}, run_after=remind_at, idempotency_key=f'reminder:{appointment_id}')` — опционально, т.к. основной путь — шедулер по колонке `remind_at`; задача-дубль идемпотентно задавится | — |
| `activities.ugc` → `jobs` | `accept_from_user(attempt_id, tg_file_id)`: внутри — `UGC.insert(status='receiving')` + `enqueue('ingest_ugc_file', {submission_id, tg_file_id}, idem='ugc_ingest:{sid}')` | — |
| `activities.ugc.approve` → `rewards` | Одна транзакция: `ugc.status='pending' → 'approved'` + `rewards.grant_on_completion(attempt_id, [{promocode, voucher, ...}])` | `ConflictError("not_pending")`, `ConflictError("duplicate_grant")` |
| `activities.photo_frame` → `jobs` | `accept_source(attempt_id, source_bytes_or_tg_file_id)`: `FrameSubmission.insert(status='queued')` + `enqueue('polaroid_render', {frame_id}, idem='polaroid:{frame_id}')` | — |
| `jobs` ↔ `ports.messenger` | Задача `telegram_send` → адаптер `messenger_outbound/outbox_enqueue.py` просто кладёт `OutboxMessage` как payload задачи; реальная отправка — в `tg_worker` через `/internal/v1/.../outbox/claim` | — |
| `media` → `ports.object_storage` | `resolve_presigned_url(media_id, actor) -> str` — проверяет права, зовёт `object_storage.presigned_get(bucket, key, ttl)` | `Forbidden`, `NotFound` |
| `personal_data` → `activities.*`, `jobs` | `confirm_forget(user_id, token)`: атомарно `users.anonymize` + `consents.revoke` + `enqueue('cleanup_ugc_files', {user_id}, idem='forget:{user_id}')` | — |
| любой модуль → `audit` | `audit.log(action: str, actor: ActorRef, object_type: str, object_id: int, details: dict)` — безопасно принимает только безПДн-детали; при попытке передать ПДн — `ValidationError` | — |

### 4.2 DTO на границах (форма данных)

```python
# core/types/dto.py (сокращённо, точные типы — в коде)

@dataclass(frozen=True)
class UserRef:
    id: UserId
    is_registered: bool          # True = ПДн заполнены и действующий Consent
    anonymized_at: datetime | None

@dataclass(frozen=True)
class ChannelRef:
    id: ChannelAccountId
    user_id: UserId
    channel_type: ChannelType
    external_id: str             # НЕ username — числовой telegram_user_id

@dataclass(frozen=True)
class AttemptRef:
    id: AttemptId
    user_id: UserId
    activity_slug: str
    status: AttemptStatus
    attempt_date: date

@dataclass(frozen=True)
class RewardIssued:
    id: RewardId
    attempt_id: AttemptId
    reward_type: RewardType
    code: str | None             # для promocode/voucher
    title: str | None
    issued_at: datetime

@dataclass(frozen=True)
class OutboxMessage:
    channel_type: ChannelType
    external_id: str
    text: str
    buttons: list[Button] | None
    media_ids: list[MediaId] | None
    idempotency_key: str         # обязателен

@dataclass(frozen=True)
class GrantSpec:
    reward_type: RewardType
    title: str | None = None
    code_template: str | None = None          # 'BIO-{random8}'
    product_recommendation_ids: list[int] | None = None
    wheel_prize_id: int | None = None
```

### 4.3 Контракты внешних границ

**4.3.1 `/internal/v1/*` (ядро ↔ `tg_worker`)** — зафиксирован в §2.6a из [05-стек.md](05-стек.md).

| Эндпоинт | Вход (JSON) | Выход (JSON) | Ошибки |
|---|---|---|---|
| `POST /internal/v1/channels/telegram/updates` | `{"update": <raw Telegram Update>, "received_at": iso8601}` | `{"status": "accepted"}` (всегда 2xx при принятии) | 401 — неверный `X-Internal-Auth`; 400 — malformed update |
| `POST /internal/v1/channels/telegram/outbox/claim` | `{"worker_id": "tg-vps-2:1", "limit": 10, "visibility_timeout_s": 90}` | `{"jobs": [{"id": …, "payload": OutboxMessage}, …]}` | 401; 503 если БД недоступна |
| `POST /internal/v1/channels/telegram/outbox/ack` | `{"job_id": …, "result": "success" \| "retryable" \| "terminal_business", "error": …?}` | `{"status": "ack"}` | 401; 404 если `job_id` не найден или не наш |
| `POST /internal/v1/channels/telegram/files/fetch` | `{"tg_file_id": "...", "job_id": …}` | `{"content_type": "...", "size": …, "download_url": "..."}` (presigned S3 URL c TTL 5m) | 401; 404 если `tg_file_id` неверный у Telegram |

**4.3.2 `/admin/*`** — только HTML (Jinja+HTMX), не JSON API. На каждом POST — `_csrf` token (double-submit), на каждом запросе — session cookie HTTPOnly/Secure.

**4.3.3 `/media/<id>`** — публичный GET; авторизация:
- гость из `tg_worker` → через HMAC-token в query (`?t=<signed>`), выдаётся ядром при подготовке сообщения;
- админ → session cookie admin'а.
Ответ: `302 Location: <presigned URL>` (TTL 5 мин) ИЛИ `403` при отсутствии прав.

### 4.4 Правило изменения контракта

Любое изменение сигнатуры функции в `__init__.py` модуля или схемы DTO:

1. Запись в журнал решений (внизу этого файла) формата `ДАТА — модуль X: сигнатура Y изменена с (…) на (…) — причина`.
2. Обновлены **обе** стороны: и экспорт модуля, и все вызывающие.
3. Соответствующие тесты обновлены первыми (TDD).
4. Если контракт лежит на границе ядро ↔ `tg_worker` (т.е. `/internal/v1/*`), владелец окна H (tg_worker) предупреждён — иначе ломается продакшн-деплой.

## 5. Адаптеры к внешним сервисам (куда класть «переходники»)

## 6. Карта владения на окна

Делю на **8 окон** (0 + 7 параллельных). Каждое окно — свой список файлов, свой `grep` запрет-зоны. В одни файлы разные окна не пишут.

## 7. Как добавить новый модуль (на будущее)

Open-source проект не планируется — секция оставлена короткой. Публикуемого ядра нет: весь репозиторий приватный, бренды и промокоды — коммерческая тайна.

**Чтобы добавить шестую активность (например, «AR-примерка макияжа» нового бренда):**

1. **Новая папка** `app/core/activities/ar_tryon/` с четырьмя файлами по шаблону: `__init__.py` (дверь), `service.py`, `state_machine.py` (если есть статусы), `repository.py` (Repo-порт для дочерней таблицы).
2. **Новое значение enum'а** `ActivityKind.AR_TRYON` в `core/types/enums.py` — **изменение контракта**, требует запись в журнал решений Окна 0 и предупреждение владельцев всех окон.
3. **Миграция** `alembic/versions/00NN_ar_tryon_tables.py` + `00NN+1_seed_ar_tryon.py` (новая дочерняя таблица + сиды активности).
4. **Реализация Repo** в `app/db/repositories/ar_tryon_repo.py`.
5. **Если нужен внешний сервис** (AR-движок): новый порт `app/core/ports/ar_render.py` + адаптер `app/adapters/ar_render/<vendor>.py` + строка в `app/config.py` (`AR_RENDER_IMPL=...`) + сборка в `adapters/ar_render/__init__.py::build()`.
6. **Регистрация в композиции** `app/main.py`: подключить новый роутер (если нужен) + новый адаптер (если есть новый порт).
7. **Регистрация в tg_worker**: новый хендлер `tg_worker/handlers/ar_tryon.py` + роутер в `tg_worker/handlers/__init__.py`.
8. **НЕ правит** `app/core/attempts/`, `app/core/rewards/`, `app/core/jobs/` — они уже умеют всё, что нужно; активность просто зовёт их `grant_on_completion`/`close_attempt`/`enqueue` через существующие двери.

## Журнал решений

- 2026-10-11 — **Выбрана раскладка Б: вертикальные срезы по активностям (`core/activities/<kind>/`) + общие горизонтальные кирпичи (`core/users/`, `core/consent/`, `core/channels/`, `core/catalog/`, `core/attempts/`, `core/rewards/`, `core/jobs/`, `core/admin_access/`, `core/audit/`, `core/moderation_queue/`, `core/personal_data/`, `core/media/`) + тонкие слои `api/`, `admin/`, `adapters/`, `workers/`, `db/`.** Причина: одна активность = одна папка = одно окно Claude = одна зона ответственности; шестая активность в будущем = одна новая папка, остальное не трогается; все пять правил соблюдаются по построению (вертикальный срез + слои; один файл — одна задача; одна дверь `__init__.py`; домен не импортирует адаптеры и SQLAlchemy; каждый вендор — за адаптером).
